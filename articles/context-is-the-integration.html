Context Is the Integration

Connecting a model to a system is now cheap. Deciding what it should see is the job.

October 6, 2026 · 4 min read · research window 2024-11-25 to 2026-10-06

On November 25, 2024, Anthropic released the Model Context Protocol, an open standard for connecting AI assistants to the systems where data lives. It shipped with reference servers for Google Drive, Slack, GitHub, Git, Postgres and Puppeteer, and with Block and Apollo as early adopters. Four months later, on March 26, 2025, Sam Altman announced that OpenAI would support the same protocol, starting with its Agents SDK. On December 9, 2025, Anthropic donated MCP to the new Agentic AI Foundation under the Linux Foundation, co-founded with Block and OpenAI and backed by Google, Microsoft, AWS, Cloudflare and Bloomberg. By then there were more than 10,000 active public MCP servers, and the protocol worked in ChatGPT, Cursor, Gemini, Microsoft Copilot and VS Code.

In about a year, the plumbing between models and enterprise systems went from vendor-specific to shared. For forward deployed engineers, whose weeks used to be full of exactly that plumbing, it changes what the deliverable is.

The integration isn't the code that connects the model to the customer's systems. It's the decision about what the model gets to see, and that decision outlives every model you'll deploy.

Before

Integration is glue code inside the app, rewritten for each model and each vendor SDK.

After

Integration is a server the customer owns, which any compliant model or client can use.

Turn

The connector outlives the model, the app and the engagement. Build it like it will.

The arithmetic is the reason this matters. Without a shared protocol, connecting M models or clients to N systems takes M×N custom integrations: five models and ten systems is fifty pieces of glue, each one breaking on its own schedule. With a protocol, it's M+N: each client implements it once and each system exposes it once, so fifteen. That isn't just less work for the vendor. Inside a customer, it means the connector you build for their claims system in month two still works when they switch models in month nine, or when a different team builds a different agent on top of it.

Before

More connectors and more tools make a more capable agent.

After

Every tool description and every returned row spends the model's limited attention.

Turn

Connecting is cheap now. Curating is the job.

Here's the catch. Once connecting a system takes an afternoon, the temptation is to connect everything and let the model sort it out. Anthropic's September 2025 guide to context engineering argues the opposite. Models don't weigh every token equally; like people with limited working memory, they have an attention budget, and it degrades as context grows. The guiding principle it offers is to find the smallest set of high-signal tokens that makes the desired outcome most likely. Forty overlapping tools, each returning an entire table by default, is the opposite of that.

So the FDE's integration work moves up a level. It's less about authentication and pagination, which the protocol and SDKs now cover, and more about design. Which handful of tools does this workflow need? What should each one be called so the model picks the right one? What should it return: the full record, or the three fields and an ID to fetch more? Those choices decide whether the agent works, and they're specific to the customer's processes in a way no vendor can make for them.

There's a security version of the same point. Every connector adds data, untrusted content or a way out, the three legs of the lethal trifecta. A protocol that makes connecting easy also makes it easy to complete the set by accident.

The integration math

3 × 10 = 30 bespoke integrations, or 13 with a shared protocol.

Every FDE has finished an engagement and watched the integration code they wrote disappear into an app nobody would maintain. The connectors were the most reusable thing built, and they were trapped inside the least reusable thing. Shipping them as the customer's own servers, with tests, owners and documentation, changes what you leave behind: not a demo that worked once, but infrastructure the customer's next team can build on.

The case against

The objections are maturity and security: the protocol is young, early servers have had real vulnerabilities, and standards have a way of being replaced. The security concern is legitimate and is a reason to scope each server tightly, with a narrow credential and a clear answer to which trifecta leg it adds. The replacement risk is smaller than it was. Governance now sits with a neutral foundation whose members include the major labs and cloud providers. And if you build thin servers over the customer's existing APIs, most of the investment is in the API and tool design, which survives a change of transport.

What this means for you

  • Inventory the integration points and decide for each: a customer-owned server, or logic that belongs inside one app.
  • Design tools for the model. Few, clearly named, with descriptions that say when to use them and when not to.
  • Trim what comes back. Return IDs, summaries and the fields the task needs; let the model ask for more.
  • Treat each server as a security boundary with its own scoped credential.
  • Hand over servers as deliverables, with tests, an owner on the customer side, and a short README.
24-hour action: List every tool your agent exposes today, with the typical size of what each returns. If any tool returns more than a few thousand tokens by default, give it a summary mode.
